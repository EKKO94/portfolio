Case study  ·  Sorba.ai  ·  AI Trainer

Preparing data
for machine learning.

I designed how people create, version and inspect datasets in Sorba’s AI Trainer. The new forms are in the demo; the wider redesign is a proposal.

Role
Sole Product Designer
Scope
Datasets · forms · visual style
Platform
Web · Desktop
Timeline
≈ 4 months

The need

A clear way to bring raw data in, version it and trust it before training.

My design

New dataset forms, now in the demo, and a proposed redesign of the module.

The outcome

The forms are live in the Sorba demo; the rest is a proposal. Feedback came from developers and the e-commerce team. No usage data.

Context

Preparing data for machine learning.

AI Trainer, formerly ML Trainer, is the part of Sorba’s platform where people prepare and version their data, create projects to analyse it and build models. Everything starts with a dataset, so this case follows that part of the product.

The project took about four months and I was its only product designer. Much of the product is under NDA and I did not keep the early files, so this case shows a selection, rebuilt from the surviving Figma screens.

The work moved fast. I researched and designed variants to solve each problem as it came up, with feedback from developers and the e-commerce team.

In the product Live
The new dataset forms, available in the Sorba demo that people can download and try. The rest of the module still uses the earlier views.
Redesign Proposal
A new overview, dataset list, version pages, explorer and warning dialogs. These are designs, not yet in the product.

My contribution

  • Redesigned many of the forms and created new forms and flows, including the dataset forms now in the demo: CSV and XLSX import, aggregation, per-field settings and a hot-data source.
  • Defined a new visual style: stronger contrast, more generous spacing and colour applied consistently to every element.
  • Proposed a redesign of the dataset list, versions, explorer and warnings, and a new overview.

I had no direct access to customers. Feedback came only from developers testing the work and from the e-commerce team. I did not document the iterations. Labels such as “OLD” and “v1” come from Figma; I do not have a dated record of their sequence or approval.

Overview · proposal

A home that shows the state of your data.

The current overview repeats navigation beside three summary cards. My proposal replaces it with summary cards, status charts, templates, favorites and an activity table.

Visual style

One look for every element.

Alongside the flows, I defined a new visual style for AI Trainer: stronger contrast, more generous spacing and a more deliberate use of colour, applied to every element so the product looks more professional.

You can see it in the proposed overview above: solid primary buttons, icon tiles on the summary cards, donut charts with counts in their legends, and a table for activity. The earlier views use outlined buttons and simpler cards.

The dataset flow

From a file to a version you can trust.

This map groups the dataset designs by task. It is a retrospective outline, and it shows which parts are live and which are proposals.

Dataset forms · live

Forms that handle real files.

An earlier saved form shows a CSV field labeled “Only .zip files are allowed”. The new form accepts CSV or XLSX by drag and drop, then asks for the format, the date field, date format, time zone and how to aggregate by time interval.

The new forms are in the Sorba demo, so anyone who downloads it can try them.

Settings for every field.

The field table offers replace and discard operations, plus LL and HL limits. Field preferences have Save and Import controls; synthetic tags and advanced rules have separate tables with Export and Import controls.

Four extra-processing options are shown: Correlation, Data Quality, Tag Ranking and Data Drift. One saved state shows Correlation selected.

Hot data source · live

Two ways to pick live data.

The hot-data source can be set up with a query in an editor, or by choosing measurements from a list. A view toggle switches between the two, so people who write queries and people who prefer a table use the same form.

Dataset module · proposal

A clearer list of what you have.

The current list holds a card per dataset. In the proposal, each card also shows a status icon, how many versions it has, a star and a selection box, so people see the state of their data before opening it.

Dataset health · proposal

Status you can read before you open it.

A dataset holds versions, and a version can fail on its own. The card shows a count of versions, and its colour and tooltip say what the count means: all good, one invalid version but still usable, or every version with issues.

Version properties show which extra processing is marked APPLIED or NOT APPLIED.

Explorer and warnings · proposal

Look before you train, think before you delete.

The proposed explorer opens a version in a summary with tabs for trend, scatter plot, box plot, histogram, correlation, data quality and data drift. Deleting a version asks for confirmation and says that it can affect models or processes that use it.

The charts in these designs use sample data.

How I worked

Working quickly with internal feedback.

Over about four months, as the only product designer, I researched and designed variants under a fast pace. Feedback came from developers testing the work and from the e-commerce team. The surviving files show variants, but I cannot connect individual changes to specific feedback.

This account combines my recollection with the surviving Figma screens. The files do not preserve a complete iteration history or a record of customer testing.

Design outcome & reflection

Forms in the demo. The rest is a proposal.

The new dataset forms are part of the Sorba demo. The redesigned overview, list, versions, explorer and warnings remain proposals, and the product still shows the earlier views there.

I do not have usage data. Next, I would observe someone importing a file and creating a first dataset version, recording completion, import errors and the points where they need help.

What I would do differently

  1. Write it down as I go

    Keep a short decision log per screen: the problem, the variants and what changed after feedback. That is the part this case cannot show.

  2. Test with the people who prepare data

    Watch someone import a file and create a dataset version; note where they stop or guess.

  3. Ship the proposal in steps

    The forms already reached the demo. The list and version status are the next smallest pieces to put in front of users.
